# 饭咔咔 FoodKaKa
## 轻量级 AI 拍照热量记账软件开发说明书

**版本：** V1.1  
**平台：** Android  
**项目类型：** 个人使用的轻量级 AI 应用  
**核心原则：** 简单、实用、低成本、免费额度优先

---

# 一、项目目标

开发一款名为「饭咔咔 FoodKaKa」的 Android 饮食记录软件。

用户可以通过拍摄食物照片，让 AI 识别食物并估算热量。用户确认或修改识别结果后，将食物记录保存到手机本地数据库，并自动计算当天已经摄入的热量和剩余热量预算。

软件主要供个人使用，不需要注册登录，不需要云同步，不追求专业营养分析和极高的识别准确率。

最终交付一个可以安装在 Android 手机上的 APK。

## 核心使用流程

首次打开：
1. 填写昵称。
2. 填写身高。
3. 填写体重。
4. 设置每日热量预算。
5. 进入首页。

日常使用：
1. 拍摄食物照片或从相册选择图片。
2. 调用视觉模型 API 识别食物。
3. 返回食物名称和估算热量。
4. 用户可以修改食物名称和热量。
5. 选择早餐、午餐、晚餐或加餐。
6. 确认保存。
7. 自动更新今日摄入量和剩余热量。

AI 无法使用时，仍然可以手动添加食物和热量。

**重要原则：AI 识别结果不能直接自动入账，必须经过用户确认。**

# 四、个人资料和计算规则

## 4.1 BMI

计算公式：

BMI = 体重（kg）÷ 身高（m）²

例如：

身高 170 cm，体重 65 kg。

BMI = 65 ÷ 1.7² ≈ 22.5。

BMI 自动计算，保留一位小数，不允许直接编辑。

## 4.2 热量计算

统一使用 kcal（千卡）。

```text
今日已摄入 = 今日所有已保存食物热量之和

今日剩余 = 每日热量预算 - 今日已摄入
```

例如：

每日预算：1800 kcal。

早餐：350 kcal。

午餐：700 kcal。

今日已摄入：1050 kcal。

今日剩余：750 kcal。

如果剩余热量小于零，显示超出预算的具体数值，不隐藏超出部分。

## 4.3 计算规则

- 仅统计已经确认保存的食物。
- 修改食物热量后重新汇总。
- 删除食物后重新汇总。
- 删除整餐后同步删除其食物明细。
- 支持补记历史日期。
- 按手机本地日期统计。
- 跨午夜后自动切换当天。
- 每天保留独立预算记录。
- 修改默认预算不修改过去日期的预算。
- 不计算运动消耗。
- 不自动生成减肥计划。

所有热量必须进行有效数值校验，拒绝空值、负数和无效输入。

使用 SQLite，首版建立以下五张表。

保存个人资料。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER | 主键 |
| nickname | TEXT | 昵称 |
| height_cm | REAL | 身高 |
| default_budget | REAL | 默认每日热量预算 |
| updated_at | TEXT | 更新时间 |

## 5.2 weight_records

保存体重记录。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER | 主键 |
| weight_kg | REAL | 体重 |
| record_date | TEXT | 记录日期 |

## 5.3 daily_budgets

保存每日热量预算快照。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER | 主键 |
| budget_date | TEXT | 日期 |
| budget_kcal | REAL | 当日预算 |

同一天只允许有一条有效预算记录。

## 5.4 meal_records

保存每餐记录。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER | 主键 |
| meal_date | TEXT | 饮食日期 |
| meal_type | TEXT | 早餐、午餐、晚餐、加餐 |
| created_at | TEXT | 创建时间 |

## 5.5 food_items

保存每餐中的具体食物。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER | 主键 |
| meal_id | INTEGER | 所属餐次 ID |
| food_name | TEXT | 食物名称 |
| calories | REAL | 估算热量 |

meal_id 关联 meal_records.id。

删除餐次时同步删除其食物明细。

新增、修改和删除数据时使用数据库事务，避免出现数据不一致。

# 六、AI 识别方案

## 6.1 模型选择

免费额度优先。

第一选择：Google Gemini API。

备用选择：OpenRouter 免费视觉模型。

开发时确认：

- 是否支持图片输入。
- 是否有实际可用的免费额度。
- 当前账号是否可以访问。
- 当前网络环境是否能够访问。
- 图片数据处理政策。
- 请求频率限制。

不要假定免费额度永久存在。

免费额度用完后暂停 AI 识别，提示用户稍后重试，不允许自动切换到付费模型。

## 6.2 图片处理

图片上传前：

- 适当压缩图片。
- 限制图片大小。
- 检查图片格式。
- 尽量移除 EXIF 位置信息。

图片识别完成、取消或失败后清理应用生成的临时图片。

不要删除用户相册中的原始照片。

## 6.3 AI 提示词

模型只需要完成以下任务：

1. 识别图片中能够辨认的食物。
2. 返回食物名称。
3. 估算每种食物的大致热量。
4. 说明不确定的内容。
5. 不要编造看不见的食物。
6. 不确定时明确说明。

不需要生成长篇营养分析报告。

## 6.4 统一 JSON 格式

模型返回数据统一转换为：

```json
{
  "foods": [
    {
      "name": "米饭",
      "calories": 230
    },
    {
      "name": "炒鸡蛋",
      "calories": 180
    }
  ],
  "total_calories": 410,
  "notes": "热量为图片估算值"
}
```

后端负责检查：

- foods 是否为数组。
- 食物名称是否有效。
- calories 是否为有限非负数值。
- total_calories 是否与食物明细总量一致。

如果模型返回格式错误，进行一次简单的解析修复或提示识别失败，不要无限重试。

前端最终使用后端统一格式，不直接依赖某个模型的原始返回结构。

# 七、成本与隐私要求

这是个人使用的软件，必须尽可能控制费用。

## 7.1 费用策略

| 项目 | 方案 |
|---|---|
| Flutter | 免费 |
| SQLite | 免费 |
| FastAPI | 免费 |
| AI API | 免费额度优先 |
| 图片处理 | 本地完成 |
| 服务器 | 初期使用个人电脑 |
| APK 构建 | 本地构建 |
| 模型训练 | 不需要 |

禁止：

- 自动购买 API 套餐。
- 免费额度用完后自动付费。
- 未经确认调用付费模型。
- 为了部署而提前购买服务器。

## 7.2 服务部署

开发初期在个人电脑运行 FastAPI 服务。

手机与电脑处于同一局域网时，可以访问电脑的服务地址。

电脑关闭后，AI 识别不可用，但本地记录、BMI 计算和手动记账仍然正常。

以后确实需要离家使用，再考虑部署到可访问的 HTTPS 服务。

## 7.3 API 密钥

API 密钥不能直接写进 Flutter 源码或 APK。

密钥保存在 Python 服务端的环境变量中。

不要将密钥打印到日志。

个人电脑上的转发服务仅用于个人试用，不要直接暴露到公网。

## 7.4 图片隐私

- 不上传用户身高、体重和历史饮食记录。
- 识别只发送当前餐食照片。
- 不主动长期保存照片。
- 不在日志中记录图片内容和 API 密钥。
- 第三方模型服务的数据处理政策必须在使用前确认。
